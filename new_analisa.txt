4. PENGGUNAAN isRunning / isSubmitting / RUNNING TASK
---------------------------------------------------------------------------
- isRunning (baru): `computed(() => Boolean(runningTaskId))` = "ADA task yang
  sedang RUNNING". Dipakai untuk:
      * menampilkan tombol Stop (Agent Input & TaskComposer);
      * indikator status UI (taskTag fallback "running").
  TIDAK dipakai untuk `:disabled` input/Submit. Input Agent selalu bisa submit.

- isSubmitting (existing: `submitting` ref): true selama request createTask
  belum selesai. Dipakai:
      * mencegah double submit (submit() menolak saat disabled=true);
      * label tombol "Sending…" + `:disabled` pada Run Task.
  Setelah respons diterima, `submitting=false` -> Send kembali tersedia
  WALAU Agent masih RUNNING. Stop (untuk task RUNNING) tetap tampil.

- runningTaskId (baru, single source of truth = TaskRecord backend):
      * diisi dari GET /api/tasks/queue (task dengan queue_state === "running");
      * diisi dari event SSE `task_started` (task yang benar-benar mulai);
      * diisi dari respons createTask bila queue_state === "running";
      * TIDAK membuat polling baru: refresh mengikuti penanda `queueRefresh`
        yang sudah ada (submit / event terminal / stop) + sekali saat mount.
  Karena id ini berasal dari queue, Stop selalu menunjuk task RUNNING yang
  sebenarnya — bukan task terakhir yang dikirim, pending, atau proposal
  Consultant.

5. HASIL VERIFIKASI QUEUE
---------------------------------------------------------------------------
Analisis alur (source-based):
  - Submit (Agent Input / Consultant Run Task) tetap lewat satu jalur:
        App.vue::submitTask -> api.js::createTask -> POST /api/tasks
        -> Global Task Queue (queue_state=pending bila slot terpakai).
  - submitTask menetapkan status tampilan dari KEBENARAN backend:
        queue_state "pending" -> task.status = "queued"  (bukan "running")
        queue_state "running" -> task.status = "running"
        selain itu            -> record.status
  - Task B/C/D yang dikirim saat A RUNNING tetap masuk sebagai PENDING
    (queued); tidak dipromosikan ke RUNNING secara optimistik.
  - Setelah Stop pada A: A -> CANCELLED; scheduler existing mempromosikan B;
    event `task_started`/refresh queue menyinkronkan runningTaskId ke B.
  - Label queued memakai token status yang SUDAH ada (`.chip.queued` /
    `.tag.queued`); lifecycle steps/index tidak diubah.

6. HASIL VERIFIKASI STOP
---------------------------------------------------------------------------
  - stopTask() target = `runningTaskId || task.id` -> menghentikan task yang
    benar-benar RUNNING (bukan task terakhir dibuat/pending/proposal).
  - Menggunakan mekanisme cancel EXISTING (api.js::cancelTask ->
    POST /api/tasks/<id>/cancel, cooperative cancellation) — TIDAK ada
    mekanisme cancellation kedua.
  - Stop tidak menimpa status tampilan task lain (`if (targetId === task.id)`).
  - Setelah Stop: queueRefresh++ + refreshRunningTask() -> target Stop
    otomatis pindah ke task RUNNING berikutnya (bila ada).
  - Stop hanya dirender saat `isRunning` true (tidak ditampilkan bila tidak
    ada task RUNNING).
