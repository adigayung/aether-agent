2. SUMBER FORMATTING COMMAND YANG DIPERBAIKI (ROOT CAUSE)
---------------------------------------------------------------------------
Lokasi: web/frontend/src/components/AgentActivity.vue (template timeline).

SEBELUM (baris RESULT):
  {{ item.success ? "✓" : "✗" }} {{ item.tool }}<template v-if="item.target"> <span class="act-target">{{ item.target }}</span></template>
SEBELUM (baris TOOL):
  <span class="fn">{{ item.tool }}</span><template v-if="item.target"> <span class="act-target">{{ item.target }}</span></template>

Akar masalah: SATU spasi pemisah itu adalah text-node whitespace-only yang
menjadi ANAK PERTAMA di dalam <template v-if="item.target">. Vue 3 (mode
whitespace default "condense") MENGHAPUS leading/trailing whitespace node,
sehingga spasi tersebut hilang saat compile. Bukti dari bundle sebelum fix:
  ... I(m.tool),1), m.target?(...) ? w("span", ..., I(m.target),1) ...
(tidak ada teks " " sebelum target) -> hasil "run_commandpython ...".

SESUDAH (fix, dipakai di TOOL dan RESULT):
  ...<span class="act-target">{{ " " + item.target }}</span>...
Spasi dipindah KE DALAM ekspresi interpolasi, sehingga menjadi node
interpolasi (bukan whitespace-only text node) dan PASTI ter-render.
Spasi tetap KONDISIONAL: hanya muncul bila item.target ada (masih di dalam
v-if="item.target"); bila argument kosong -> tidak ada spasi tambahan.

Bukti dari bundle SETELAH fix (dist/assets/index-34IyEPZa.js):
  TOOL   : w("span", sv, I(" "+m.target), 1)
  RESULT : ... st(I(m.success?"✓":"✗")+" "+I(m.tool),1), ... w("span", iv, I(" "+m.target),1)
=> "✓ run_command" + " " + "python scripts/check_code_editor.py".

Bukti (file:line):

  - (c) TIDAK ADA cabang berdasarkan sumber task. web/django_app/api/services.py::
    create_task (L842) TIDAK PERNAH memanggil _start_execution lagi; di ujungnya

  - (b) BENAR (akar masalah). web/frontend/src/App.vue::submitTask sebelumnya:
        task.status = record.status || "prepared";
    `record.status` dari gateway SELALU "prepared" (create_task membuat
    TaskRecord(status="prepared"); promosi slot hanya mengubah `queue_state`).
    Sementara `isRunning` (App.vue L136) menganggap "prepared" sebagai RUNNING:
        ["running","prepared","planning","executing","validating"].includes(status)
    Akibatnya task yang di backend ber-queue_state="pending" (menunggu slot)
    tetap tampil "Running…" di Workbench (Stop button, composer disabled, chip
    "Task: Running"), sehingga user melihat "task langsung running" dan tombol
    yang tersedia adalah STOP/CANCEL (bukan Disable) -> persis keluhan
    "tidak bisa entry pending/disabled".

BUKTI EMPIRIS bahwa jalur Workbench sudah melewati queue yang sama (sebelum
perubahan frontend apa pun): skenario baru [9] (POST /api/tasks via HTTP, layer
yang sama dengan Workbench) LULUS pada kode backend yang ada ->
  A (slot kosong)  -> queue_state="running"
  B, C (slot dipakai) -> queue_state="pending"
  disable/enable pada B dari Workbench -> OK
  A selesai -> B running -> B selesai -> C running (FIFO, max concurrency=1)
Jadi TIDAK ada perubahan backend yang diperlukan.
