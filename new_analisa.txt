2. PERUBAHAN UTAMA PER FILE

web/django_app/api/services.py
- __init__: tambah self._pumping = False (penjaga re-entrancy pump; BUKAN
  sumber kebenaran status slot).
- create_task(): TIDAK lagi memanggil _start_execution langsung. Sekarang:
    if self.auto_execute: self._scheduler_pump()
  Task baru SELALU masuk antrian sebagai queue_state="pending" (default
  TaskRecord), lalu dipromosikan ke "running" oleh pump BILA tidak ada blocker.
- _scheduler_pump()  [BARU]: satu-satunya pemilih task berikutnya.
    * di dalam self._lock: bila self._cancel_tokens tidak kosong ATAU ada
      task queue_state=="running" -> slot terpakai, return (menutup race Stop
      vs scheduler; menjamin tidak pernah 2 eksekusi paralel).
    * pilih kandidat = queue_state=="pending" && status not in
      (completed,failed,cancelled), urut (queue_order, task_id) -> FIFO.
    * tandai slot ATOMIC: candidate.queue_state="running" + buat & daftarkan
      CancellationToken (sinkron, sebelum thread jalan).
    * keluar lock, lalu run_in_background(_execute_task) -> TIDAK menahan lock
      saat TaskExecutor bekerja.
    * kegagalan start: pulihkan queue_state="pending" + buang token (anti stall).
- _start_execution(): dipertahankan untuk kompatibilitas pemanggil existing/
  verifier; kini juga memastikan slot "running" bila masih pending.
- _execute_task(): dibungkus try/finally -> _run_task_inner() menjalankan isi.
    finally SELALU melepas slot:
      - pop cancellation token (semua path, termasuk exception),
      - queue_state -> "done" bila masih "running" (anti nyangkut),
      - panggil _scheduler_pump() -> task berikutnya (FIFO) mulai.
  Ini TITIK PELEPASAN SLOT di gateway (BUKAN di runtime.py).
- _run_task_inner(): isi eksekusi (dipisah agar finally di atas bersih).
- set_queue_state(): setelah disable/enable, panggil _scheduler_pump() (di luar
  lock). Enable bisa langsung mempromosikan ke RUNNING sesuai queue_order.
- cancel_task(): bila task dibatalkan saat BELUM running (tidak ada token),
  pump dipanggil agar antrian bergerak. Bila RUNNING, slot dilepas oleh
  _execute_task.finally setelah cancellation mencapai terminal state.
- _update_task_status(): tidak diubah — tetap menyetel queue_state
  "running"/"done" sebagai proyeksi UI.

--------------------------------------------------------------------------------
3. CARA KERJA SCHEDULER SEKARANG
--------------------------------------------------------------------------------
Struktur: satu queue GLOBAL (self._tasks) + satu scheduler + SATU execution
slot. Consultant dan Workbench membaca/menulis queue yang sama.

Alur:
  create_task(auto_execute=True)
      -> TaskRecord(queue_state="pending", queue_order=++seq)
      -> _scheduler_pump()
            slot bebas? -> promote ke "running" (atomic di lock)
                        -> run_in_background(_execute_task) di luar lock
            slot terpakai? -> tetap "pending"
  _execute_task(...)
      -> TaskExecutor.run(...)  (AgentRuntime/AgentOrchestrator TIDAK diubah)
      -> on_status(...) -> _update_task_status (status lifecycle)
      -> finally: lepas token + queue_state="done" + _scheduler_pump()
  _scheduler_pump() lanjutan memilih pending berikutnya menurut queue_order.

Jaminan:
- Concurrency = 1 (slot tunggal; cek token+running di dalam lock).
- FIFO by queue_order; Move Up/Down (move_task) mengubah queue_order -> benar-
  benar mengubah task berikutnya.
- Disabled TIDAK pernah dipilih (kandidat hanya queue_state=="pending").
- Disable != Cancel; Cancel/Stop tetap memakai CancellationToken (primitif
  tunggal). Slot dilepas hanya setelah execution benar-benar berakhir.
- auto_execute=False: TIDAK ada eksekusi (kontrak verifier lain tetap utuh).
- Lock TIDAK ditahan saat TaskExecutor bekerja.
