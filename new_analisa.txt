AETHER CONSULTANT SYSTEM
=======================
Laporan implementasi faktual (bukan rencana). Semua klaim di bawah diverifikasi
dengan menjalankan kode (scripts/check_consultant.py) dan build frontend.

1. OBJECTIVE
------------
Menjadikan Consultant sebagai "otak" AETHER yang TERPISAH dari Agent:

    User
      -> Consultant (Project Intelligence + Investigation + Validation +
                     Recommendation + Task Generator)
      -> Task Proposal
      -> User klik Run Task
      -> Agent (executor yang mengubah project)

Boundary inti:
    CODE PROJECT   -> Consultant READ ONLY
    PROJECT BIBLE  -> Consultant READ + UPDATE

Sebelum task ini, Consultant hanya UI dummy di frontend (modal chat dengan
pesan hardcode + setTimeout "respons dummy"), tanpa backend, tanpa Project
Bible, tanpa tool, tanpa boundary.

3. CONSULTANT ARCHITECTURE (SESUDAH)
------------------------------------
Package baru `src/agent_ai/consultant/` yang MERAKIT komponen AETHER existing
(bukan subsystem baru yang menduplikasi):

    consultant/service.py  -> ConsultantService.consult(): satu giliran
                              konsultasi. Memakai AgentOrchestrator
                              (run_continuous_loop) + ToolExecutor + curated
                              ToolRegistry + ProjectBrain.
    consultant/tools.py    -> registry Consultant yang DIKURASI (read-only +
                              update_project_bible) + guard run_command.
    consultant/policy.py   -> PermissionManager read-only (memakai permission
                              layer existing).
    consultant/prompt.py   -> system prompt Consultant (peran + boundary +
                              format Task Proposal).
    consultant/models.py   -> ConsultantTurn / ConsultantResult (data saja).

Reasoning loop TIDAK dibuat baru: memakai `agent_ai.core.orchestrator`
(continuous loop Native Tool Calling) yang sama dengan Agent, tetapi dengan
system prompt, tool set, dan permission policy yang berbeda.

Alur backend:
    HTTP POST /api/consultant/consult
      -> GatewayService.consult()
           -> resolve root project + provider (konfigurasi LLM SQLite)
           -> ConsultantService.consult()
                -> AgentOrchestrator.run_continuous_loop()
                     -> provider.generate (LLM, bebas memilih tool)
                     -> ToolExecutor -> curated registry (permission enforced)
                     -> ProjectBrain (Project Bible context)
                -> reply + tool_events + task_proposal
      -> JSON response

4. PROJECT BIBLE INTEGRATION
----------------------------
- Baca (READ): ConsultantService membangun
  `ProjectBrain.for_project(root, provider=...)` dan meneruskannya ke
  AgentOrchestrator. Orchestrator menyisipkan `brain.get_context()` sebagai
  system message ("# Project Intelligence") di awal percakapan continuous loop.
  => Consultant SELALU membaca Project Bible sebagai konteks awal.
  Diverifikasi: scripts/check_consultant.py [1b] memeriksa message provider
  memuat "# Project Intelligence".
- Update (WRITE): tool `update_project_bible` (ConsultantBibleTool) menulis ke
  `<root>/.aether/bible/<kategori>.md` memakai `IntelligenceLearner.add_verified`
  + `BibleStore` existing (dedupe + validasi kategori). LLM menentukan sendiri
  kapan memakainya (tidak ada rule artificial "hanya boleh saat X").
- Tidak ada store pengetahuan baru (tidak ada ConsultantBible/KnowledgeStore/
  MemoryStore). Knowledge tetap di AI Project Bible existing.

5. PROJECT ANALYSIS
-------------------
Consultant dapat membaca project aktif dengan tool read-only yang sudah ada:
list_files, read_file, search_code (memakai tools/filesystem.py existing,
dibatasi ke root project). Tool ini adalah cara utama membaca source/workspace.
Root project berasal dari active project (SQLite) atau project_id; fallback ke
root workspace AETHER bila belum ada project aktif.

6. INVESTIGATION / DIAGNOSTIC CAPABILITY
----------------------------------------
Multi-step investigation dikendalikan LLM lewat continuous loop existing:
LLM memanggil tool -> hasil tool dikembalikan (role "tool") -> LLM lanjut ->
... sampai LLM memberi jawaban final tanpa tool call. Tidak ada keyword planner
deterministik. LLM bebas menentukan tool, urutan, dan kapan cukup.

7. TERMINAL CAPABILITY
----------------------
Tool `run_command` (ConsultantRunCommandTool) mewarisi RunCommandTool existing
(routing Windows-aware shell/native, timeout, output terstruktur). Consultant
dapat menjalankan diagnosis/validasi: git status/diff/log, python checker,
pytest, npm run build, dll.

8. READ-ONLY PROJECT BOUNDARY
-----------------------------
Boundary berlapis (defense in depth):
(a) Registry dikurasi: hanya list_files/read_file/search_code/run_command/
    update_project_bible. write_file/edit_file/delete_file/move_file TIDAK
    didaftarkan -> tidak dapat dipanggil lewat tool.
(b) Permission policy (memakai layer existing agent_ai.permission):
    READ_ONLY=ALLOW, WORKSPACE_WRITE=DENY, DELETE_MOVE=DENY,
    COMMAND_EXECUTION=ALLOW, EXTERNAL_NETWORK=DENY, UNKNOWN=ALLOW (untuk tool
    Bible yang dikurasi).
(c) Guard command: menolak command destruktif (git commit/push/reset/clean/
    checkout/..., del/rmdir/move/ren/copy/mkdir/..., redirect ">" di luar quote).
Guard (c) best-effort (bukan sandbox penuh) — dicatat sebagai limitation.
Diverifikasi: check_consultant.py [3][4][5][5b] (tidak ada file source dibuat
saat LLM meminta write_file).

9. BIBLE UPDATE BEHAVIOR
------------------------
Satu-satunya jalur tulis Consultant adalah `update_project_bible` ke Project
Bible. Tidak menulis source. LLM memutuskan kapan knowledge layak disimpan
(fakta/keputusan/pelajaran). Duplikat di-skip; knowledge lama dipertahankan.
Diverifikasi: check_consultant.py [2].

10. VALIDATION / VERIFICATION
-----------------------------
Consultant dapat menjalankan test/build/lint/checker/diagnostic via run_command.
System prompt mewajibkan membedakan "eksekusi selesai" vs "requirement
terverifikasi" dan menyatakan "belum terverifikasi" bila tidak dapat dibuktikan.
Tidak ada klaim palsu: verifikasi tetap hasil tool nyata.

11. RECOMMENDATION FLOW
-----------------------
Jawaban Consultant (teks markdown) memuat findings, diagnosis, rekomendasi,
opsi, trade-off, affected files, dan dampak. Frontend merender markdown via
renderer bersama (markdown.js). Consultant TIDAK mengimplementasikan source.

12. TASK PROPOSAL FLOW
----------------------
System prompt meminta LLM membungkus Task Proposal dengan blok berpagar
```task ... ```. `extract_task_proposal()` mengekstrak isi blok tersebut.
Response API memuat field `task_proposal` (Nullable). Frontend menampilkan
kartu "Task Proposal" + tombol Run Task. LLM yang menentukan kapan membuat
proposal (bukan rule kaku).
Diverifikasi: check_consultant.py [1][7].

13. CONSULTANT -> AGENT FLOW
----------------------------
Frontend: tombol Run Task memancarkan event `run-task` dengan teks proposal ->
App.runConsultantTask(text) -> submitTask(text) -> createTask() (endpoint
/api/tasks existing) -> Agent Runtime existing. Consultant tidak menjalankan
eksekusi; Agent tetap eksekutor.
Diverifikasi: check_consultant.py [7b] (task_proposal -> create_task existing).

14. TASK QUEUE INTEGRATION
--------------------------
TIDAK membuat queue subsystem baru. AETHER existing mengeksekusi task pada
background daemon thread per task (`api/execution.py: run_in_background`); tidak
ada queue/worker framework. Karena itu "task masuk queue bila Agent sedang
running" TIDAK diterapkan literal (tidak ada queue di AETHER) dan TIDAK dibuat
queue baru sesuai instruksi. Task Proposal dikirim lewat alur task existing
(create_task). Dicatat sebagai MISSING/limitation (lihat #24/#27).

15. SESSION CONTEXT
-------------------
ConsultantService menyimpan konteks percakapan per `session_id` (in-memory
proses; kelas ConsultantSession). Giliran sebelumnya disertakan pada giliran
berikutnya (build_task menyertakan riwayat, dibatasi 12 pasangan turn terakhir).
Frontend menyimpan `session_id` dan mengirimnya pada setiap request, sehingga
"kenapa X?" -> "bagaimana memperbaikinya?" -> "buat task" memakai investigasi
sebelumnya tanpa mengulang dari nol.
Diverifikasi: check_consultant.py [6].

16. PROJECT LEARNING LOOP
-------------------------
Hasil Agent terbaca kembali oleh Consultant: (a) Project Bible diperbarui oleh
AgentRuntime (`_record_project_learning` -> brain.learn) dan oleh Consultant
(tool update_project_bible); (b) `.aether/log/<task_id>.log` (hasil/aktivitas
Agent) dapat dibaca Consultant lewat tool (read_file/list_files) maupun dari
root project. Consultant hanya membaca hasil dan menyimpan knowledge relevan.
Tidak mengubah source dari hasil Agent.

17. WEB ACCESS
--------------
AETHER memiliki FONDASI browser/web tool (`src/agent_ai/browser/`: HttpFetchTool,
HtmlParser, BrowserToolRegistry) tetapi belum terintegrasi ke tool registry Agent
(`build_registry` tidak mendaftarkannya) sekaligus belum diekspos ke Consultant.
Untuk task ini web access TIDAK diaktifkan dan TIDAK dibuat tool web palsu.
Arsitektur Consultant sudah siap menerimanya: tambahkan HttpFetchTool ke curated
registry + ubah policy EXTERNAL_NETWORK dari DENY ke ALLOW saat capability itu
resmi tersedia. Dicatat sebagai capability belum tersedia (lihat #24).

24. MISSING / NOT AVAILABLE
---------------------------
- TASK QUEUE: AETHER tidak punya queue subsystem; eksekusi per-task memakai
  background daemon thread. Task Proposal yang dikirim saat Agent running
  berjalan paralel (bukan antre). Tidak dibuat queue baru.
- WEB ACCESS: fondasi browser/web tool AETHER ada (src/agent_ai/browser) tetapi
  belum terintegrasi ke registry Agent/Consultant. Tidak diaktifkan.
- PERSISTENSI SESSION CONSULTANT: konteks sesi in-memory (per proses). Hilang
  saat proses Django restart (persistent knowledge tetap Project Bible).
- UI approval/permission dialog: tidak ada (policy Consultant deterministik).
- Markdown renderer: tabel belum didukung (sama seperti ReportViewer existing).

27. KNOWN LIMITATIONS
---------------------
- Guard command (c) bersifat best-effort; tidak mencegah semua bentuk modifikasi
  (mis. skrip python yang menulis file). Boundary utama tetap registry (tanpa
  tool tulis) + permission policy.
- Konteks sesi in-memory (tidak persisten setelah restart).
- Request konsultasi bersifat sinkron (menunggu loop selesai) — untuk aplikasi
  single-user lokal; belum streaming.
- Biaya/langkah dibatasi max_steps=40 per giliran (safety, bukan target).
- Provider harus tersedia (kredensial valid); bila tidak, API mengembalikan
  ValidationError dengan pesan jelas.
- Klasifikasi policy memakai UNKNOWN=ALLOW untuk tool Bible (registry dikurasi),
  bukan pola umum.
- Task Queue tidak diterapkan (lihat #14/#24).

29. FINAL ARCHITECTURE SUMMARY
------------------------------
Consultant = reasoning layer AETHER yang memakai loop/tool/Bible/permission
existing dengan boundary read-only terhadap CODE PROJECT dan read+update
terhadap PROJECT BIBLE. Ia menghasilkan Recommendation + Task Proposal; Agent
tetap satu-satunya eksekutor (Task Proposal dikirim via alur task existing).
Integrasi: Vue.ConsultantChat -> POST /api/consultant/consult ->
GatewayService.consult -> ConsultantService -> AgentOrchestrator(continuous
loop) + curated registry + ProjectBrain. Tidak ada queue/Bible/knowledge/store
duplikat; web access tidak difake. Semua verifikasi kode di atas LULUS.
